# 4.5 silent video, re-encoded timecode, and track-order validation — 2026-09-20

## Scope

A generated MOV containing video and a timecode track, without audio, exposed a
conversion failure in the ProRes preset. ProRes and Proxy both required an audio
stream through `-map 0:a`. Their default maps now use `0:a?`, matching the other
supported video presets. Explicit audio routing still requires the selected
streams; audio-only export still requires audio.

The shared-job regression converts that silent source to ProRes and Proxy with
three captured timecode policies: preserve `01:02:03:04`, replace it with
`02:03:04:05`, and disable timecode. Each output must match its planned URL,
contain 24 frames and no audio, expose the requested timecode, and decode using
the expected video codec.

A second live regression generates two mono PCM tracks containing distinct
440 Hz and 880 Hz tones. A captured routing plan reverses their order before
ProRes export. The output must contain two mono 48 kHz streams, and decoding each
stream to PCM must yield one second of samples with the expected tone frequency.
This verifies content and order, beyond checking the stream count.

The shared test wait helper now immediately reports a terminal state that does
not match the expected state, including the executor diagnostic, instead of
reporting a misleading timeout.

## Remaining limits

These generated fixtures use the shared service with an injected unrestricted
file authorizer. They do not prove real bookmark access, named MCP client
behavior, or representative in-app playback. The codec/timecode matrix is
bounded to the cases above; other frame rates, drop-frame timecode, additional
routing modes, longer programs, and other hardware remain release validation
work. ProRes and Proxy use the hardware encoders selected by their presets on
this Mac.
