# 4.4 subtitle and remote coordination review

## Supported scope and changes

Subtitle ownership previously used an instance-local lock. Two app processes could
both validate the same previous SRT generation before either replaced it. Publication
now takes a nonblocking exclusive `flock` on the destination directory inode around
metadata preparation, ownership revalidation and publication. Directory aliases
therefore share the lock. A busy or unsupported lock fails publication without
modifying the destination; a later retry may proceed. Closing the descriptor releases
the lock, including process exit. No lock sidecar is created or removed.

Reservations remain in-process: simultaneous processes can select the same output
name, but only one can publish successfully. The later attempt either encounters the
busy lock or rejects the changed ownership generation. This is deliberately a
failure-and-retry policy rather than an automatic rename after transcription.

Remote uploads previously had no same-destination coordination across service
instances or app processes. `RemoteUploadLease` now holds a nonblocking file lock
through the actual rclone upload. Its key includes backend, normalized server/port,
S3 endpoint/bucket, SMB share, remote directory and filename. Credentials and profile
identity are excluded, so different accounts configured for the same object still
contend. Names are case-folded conservatively. Different filenames can proceed
concurrently. A competing upload receives a retryable explanatory failure before
rclone copy starts. Sequential rclone overwrite behavior is unchanged.

Remote lock files contain no connection details; their names are SHA-256 digests of
structured key data. They live in the app's Application Support UploadLocks directory,
are opened without following symlinks and are never unlinked. Descriptor close is
idempotent and also runs during lease destruction, so a late duplicate release cannot
close a descriptor reused by a subsequent upload. `O_CLOEXEC` prevents child processes
from retaining the lock after the app releases it.

## Evidence

- `python3 -m unittest discover -s scripts/tests -p test_subtitle_coordination.py -v`
  passed both tests on 2026-09-11. The tests compile the production subtitle naming
  source and launch a separate publisher process while the parent holds a filesystem
  lock. They verify rejection preserves both existing and staged subtitles, a later
  retry replaces the owned output, and a symlinked directory observes the same lock.
- `scripts/tests/test_remote_upload_coordination.py` passed three real-process
  tests compiling the production lease: normalized destination contention and
  retry, independent filenames, and lock release after SIGKILL with the same inode.
- `RemoteUploadLeaseTests` covers overlap across profiles and normalized names,
  release/retry and duplicate release, concurrent distinct filenames, and refusal to
  follow a planted lock symlink while preserving its target.
- A fresh focused Xcode test attempt could not resolve package dependencies because
  GitHub DNS was unavailable. The root release validation run supplies the XCTest
  result using cached packages; do not interpret this review alone as a passing
  app test report.

## Limits and release disposition

The supported coordination scope is cooperating current app instances under the same
macOS user/app container. Older app versions, unrelated subtitle editors, remote
clients on another machine, and different sandbox containers do not participate.
Network filesystem `flock` behavior depends on the mounted filesystem; inability to
acquire a subtitle publication lock fails closed. No network-volume validation was
performed in this review.

Remote endpoint aliases, server-side path aliases and different backend routes to the
same object cannot be reliably identified from local configuration. Concurrent writes
through those routes, or through unrelated clients, require server-side coordination
and remain outside the supported upload scope. Users should give such producers
distinct destination names or directories. The implementation does not claim a
universal remote conditional-write guarantee across FTP, SFTP, SMB and S3, and this
review did not make live remote transfers.

Within the defined cooperating-app scope, the reproducible local coordination gaps
have been constrained. Manual network-volume and live remote validation remain in
the release checklist; this review does not replace them.
