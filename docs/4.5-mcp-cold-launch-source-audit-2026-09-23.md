# 4.5 MCP cold-launch source audit — 2026-09-23

This audit checked the helper-triggered app launch path in the current source
after the installed build 577 returned a launch error in the restricted command
sandbox. It did not alter the installed app, Agent Access preference, or MCP
client configuration.

## Findings

- `AgentHelper/AagedalMediaConverterMCP.swift` first checks for the app's
  `CFMessagePort` endpoint. If absent, it asks Launch Services to open the app
  bundle containing that helper with running-application substitution disabled.
- The helper polls for the endpoint while the asynchronous launch is pending,
  pumps its main run loop for the Launch Services callback, and bounds a pending
  launch to 30 seconds. After a successful callback it waits up to ten seconds
  for an endpoint; a launch error and a missing endpoint have distinct errors.
- `Aagedal_Media_Converter_App.swift` restores persisted agent jobs before it
  reconciles Agent Access. `ApplicationAgentAccessLifecycle` starts the endpoint
  only if the current `localAgentAccessEnabled` preference is true. Startup
  rechecks that preference so a concurrent disable does not reopen access.
- The installed build 577 tested earlier predates the current helper polling
  change, and its Agent Access preference was disabled. Its sandboxed launch
  error does not reproduce a defect in the current source or prove a successful
  cold launch from a named client.

No additional code change follows from this source review. A fresh packaged
build with Agent Access enabled must be tested through an actual named client's
`list_presets` call in a normal login session, starting with the app closed.
The acceptance result must include a successful preset response, not merely
MCP initialization or a structured transport error.

## Validation

`python3 -m unittest scripts.tests.test_mcp_helper -v` passed all seven
process-level helper framing and discovery tests against a freshly compiled
helper. Those tests do not exercise Launch Services or the app endpoint.
