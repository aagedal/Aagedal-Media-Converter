# 4.5 exact-output validation — 2026-09-19

## Scope

The service checks all planned outputs before starting a batch, but a later file
can become occupied while an earlier file is converting. The converter previously
chose a suffixed filename in that case. Because the adapter checked only whether
the accepted output existed, it could report success against the colliding file.

Shared requests now carry their required final output URL into the converter.
The converter checks the resolved filename and reserves that exact path under
the same lock used by legacy output reservations. Existing files, source-path
collisions, and active converter reservations fail with `output_collision`.
Rejection occurs before registering the output for cleanup. Legacy requests
without a required path continue to choose unique names.

## Validation

- A live two-file Stream Copy test inserts another operation's output immediately
  before the second converter call, after service execution validation. It checks
  the failed diagnostic, unchanged colliding contents, no suffixed output, and
  successful decoding of the first completed output.
- Initial application-job run: 62 passed; the new test's directory comparison
  failed solely on macOS `/var` versus `/private/var` URL spelling. The assertion
  now compares filenames within the same destination directory.
- Full Debug unit target: 953 tests passed, including the corrected live batch
  regression and legacy unique-name/source-protection tests.
- `git diff --check`: passed.

## Remaining release gates

This closes silent output renaming at converter admission. It does not provide
an atomic cross-process filesystem reservation against external writes after
admission. Specialized post-conversion publication, live manual/agent overlap,
real folder-grant recovery, named-client workflows, playback, bilingual visual
review, and Developer ID signing/notarization remain in the release plan.
