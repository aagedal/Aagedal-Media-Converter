# 4.4 Matroska channel-layout presentation review

Reviewed 2026-09-11.

## Finding

The pinned SwiftMediaMetadata 3.0.0 Matroska reader synthesizes every audio
`channelLayout` from the channel count. Its `defaultLayout(forChannels:)` maps
three channels to `2.1`, four to `4.0`, six to `5.1`, and eight to `7.1`.
The reader does not decode speaker-layout information before assigning those
values. A channel count cannot distinguish, for example, three front channels
from stereo plus LFE, or side surround from rear surround.

The application's MPV track menu independently labeled six and eight channels
as `5.1` and `7.1` using only channel counts.

## Changes

- Mapped MKV/WebM metadata omits the inferred layout while retaining channel
  counts, stream indices, codec information, and sample rates. Metadata panels
  and metadata exports therefore no longer assert a guessed speaker arrangement.
- The audio routing menu applies the same mapping to its detailed metadata.
  Its existing channel-count fallback describes multichannel tracks as `N ch`.
- The MPV track menu uses its existing `N ch` formatting for six and eight
  channels. Mono/stereo conventions in the track menus remain unchanged.
- Other containers retain their reported layout, including `5.1(side)`.
- Both AVC-Intra mono-splitting paths duplicate the decoded stream with `asplit`
  and extract each channel with `pan=mono|c0=cN`. They no longer force a guessed
  speaker layout with `channelsplit`, preserving channel order and samples even
  when the metadata's inferred speaker arrangement is wrong.

The presentation changes do not modify source container bytes or channel counts.
`MatroskaMuxer` writes channel counts and the supplied encoded audio data; it
does not infer or write a speaker-layout label.

## Validation

`MatroskaLayoutPresentationTests` covers both MKV and WebM, counts one through
eight, preservation of stream identity/codec/sample rate/count, preservation of
the raw input metadata, and retention of explicit MOV/MP4 layouts. The coordinated
release-preparation unit suite runs these tests with the other regressions.

`testAVCIntraPositionalSplittingPreservesMatroskaChannelSamples` generates 3.0 and
5.1(side) MKV inputs with a distinct constant sample value in every channel. It
runs the real AVC-Intra command-builder graph, then decodes all eight output
mono tracks and checks every sample against the corresponding input value
(tolerance 0.000001), including zero-valued padding tracks. This checks audible
data preservation despite the source parser reporting misleading layouts.

The existing generated multichannel downmix regression now expects an unknown
Matroska layout while retaining its conversion and stereo-output checks.

Static inspection confirms the audio-routing plan consults a layout only for
two-channel splitting, whose existing fallback is `stereo`. Track selection,
channel extraction, channel swapping, and downmix planning use indices/counts.

## Remaining limitation

The parser still lacks verified speaker positions. `FFMPEGProbeService`
consumes the mapped metadata, so its Matroska layouts are unknown too. The two
AVC-Intra splitters no longer require layout strings. They preserve decoded channel order
without asserting which speaker each channel belongs to. Speaker-aware downmix
continues to rely on FFmpeg decoding the source's actual codec metadata.

Revisit the mapping when SwiftMediaMetadata exposes verified layout provenance;
the current policy intentionally hides all MKV/WebM layout strings.
