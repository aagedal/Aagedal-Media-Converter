# 4.5 preview keyboard validation — 2026-09-20

## Findings and change

Both unchanged native and MPV seek/screenshot/playback/reopen UI tests passed on
repeat (2 tests, zero failures), before the keyboard fix. The earlier failures
recorded in [the preview validation](4.5-preview-validation-2026-09-20.md) are
therefore intermittent. DisplayManager infinite-rectangle warnings still occurred
on the passing run, so those warnings alone do not identify a playback failure.

Code inspection found a separate concrete input bug: an app-wide preview event
monitor always consumed Command-A to toggle the audio meter, including when a
text field or another window owned keyboard input. Preview playback handlers
also interpreted cursor keys and other text-input keys as playback commands.

The audio-meter shortcut now uses the existing backend handler, whose event
monitor is scoped to its own key window. The shared handler defers to AppKit
when an NSTextView or NSTextField is first responder. This preserves selection,
cursor movement, and editing while retaining playback shortcuts outside editing.

Both backend UI tests now activate the app before opening the preview, explicitly
focus the timecode editor, collapse its initial selection, then verify Command-A
replaces the entire value and leaves the audio meter unchanged. They retain
seeking, frame capture, playback advance/pause, closing, and reopening checks.

## Remaining limits

A passing repeat does not explain or eliminate all prior event-delivery stalls.
Stitching sequence playback, native/MPV transitions between trimmed clips,
real card/MXF media, and broader manual playback remain separate release gates.
This change does not claim those checks or OS-level sandbox access validation.
