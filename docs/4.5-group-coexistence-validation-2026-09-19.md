# 4.5 group coexistence validation — 2026-09-19

## Scope

Two regression tests connect the real `ConversionManager.convertGroup` entry
point and `ApplicationJobService` through one execution gate. Earlier tests held
the gate directly to model legacy ownership; these tests let the manager acquire
and release it while its source-details preparation is suspended.

- An agent submission stays queued while the legacy group owns execution.
- Cancelling all legacy work releases the waiting agent job, which succeeds.
  Late source-details completion cannot revive the cancelled legacy row.
- Cancelling the waiting agent leaves legacy rows and execution ownership intact
  and never calls the agent executor's cancellation callback.
- After the legacy group is cancelled, a replacement agent job succeeds. The
  cancelled agent waiter neither executes nor stalls subsequent work.
- Final shared records contain exactly one success and, in the agent-cancellation
  case, one cancellation.

No production, schema, UI, dependency, or bundled-binary changes were needed.

The initial sandboxed build could not write compiler/package caches. The approved

These are deterministic ownership tests with injected source details and a
controlled agent executor. The group contains one item with concatenation and
post-actions disabled; no media subprocess is launched by the new tests. They do
not establish live merge/export overlap, encoding-time cancellation isolation,
post-action coexistence, first-party bookmark access, or playback. Those checks,
named-client acceptance, and signed Release packaging remain release gates.
