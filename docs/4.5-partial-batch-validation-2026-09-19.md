# 4.5 partial-batch validation — 2026-09-19

## Scope

A sequential batch could complete one output and then fail or be cancelled on a
later source. The completed file remained on disk, but the terminal record had
an empty `outputURLs` list and every queue row inherited the batch failure.

The FFmpeg adapter now retains each successfully completed output and includes
that ordered list in failure and cancellation results. The service accepts only
a prefix of the planned output list for those results; successful execution still
requires the entire exact list. This prevents a malformed partial result from
being associated with the wrong source row. Validation also applies when the
service has already recorded a cancellation request.

The existing schema-v1 `outputURLs` field stores these results without a schema
change. A failed or cancelled job may therefore have completed outputs. Its job
state and diagnostic continue to describe the batch, while the corresponding
completed source rows appear done with full progress and output-file access.
The active interrupted conversion is not counted as completed merely because a
file exists. Sources beyond the completed prefix retain the batch terminal state.

- Cancellation during the second runner call: the first completed output remains

The initial sandboxed Xcode attempt could not write compiler/package caches.
The focused rerun with the required cache access passed. No bundled binaries,

## Remaining release gates

This does not establish durable per-file checkpoints during a running batch:
app termination before its terminal record is persisted still follows the
existing interrupted-job policy. Live visual review of mixed-result queue rows,
publication-boundary cancellation, named-client workflows, real grant recovery,
specialized-job coexistence, and Developer ID signing/notarization remain open.
