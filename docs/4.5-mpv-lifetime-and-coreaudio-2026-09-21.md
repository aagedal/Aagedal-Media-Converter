# MPV lifetime and CoreAudio investigation — 2026-09-21

## App changes

`MPVPlayer` previously registered `Unmanaged.passRetained(self)` as the C wakeup
context, releasing it only in `deinit`. That cycle prevented destruction of every
initialized player. The context now retains a separate box whose handler captures
the player weakly. The C callback schedules work without resolving the weak owner
on libmpv's callback thread. This matters because libmpv invokes callbacks under
its wakeup mutex: releasing the last player reference inside that callback could
otherwise deadlock while unregistering it.

Teardown unregisters the callback before releasing the box and handles destruction
on the event queue without synchronously dispatching back onto the same queue.
Queued handlers survive release of the box and safely ignore a released player.
Shutdown events also unregister the callback before destroying the handle.

Four property observers read `MPV_FORMAT_FLAG` as `Int32`, matching libmpv's C
`int` payload. They previously read an eight-byte Swift `Int`, overreading the
four-byte flag. This is independent of the CoreAudio crash.

`MPVWakeupContextTests` covers weak ownership, dispatch onto the event queue after
box release, and release of an actual initialized player after attaching its
Metal layer. The last test loads no media and does not validate audio output.
The parent continuation records the combined XCTest/UI results separately.

## Dependency crash diagnosis

The retained app crash signature matches upstream
[mpv issue #18274](https://github.com/mpv-player/mpv/issues/18274): `mp_msg_va →
mp_msg → hotplug_cb` on CoreAudio's notification queue. The upstream maintainer
[closed that issue with PR #18383](https://github.com/mpv-player/mpv/issues/18274#issuecomment-5496436665).

[PR #18383](https://github.com/mpv-player/mpv/pull/18383) addresses a concrete
failure path present in the local 0.41.0 source: `init()` registers the hotplug
callback before initializing the AudioUnit, then returns on initialization
failure without unregistering the callback. The audio-output object can be freed
while CoreAudio retains its raw callback context. This supports an initialization
failure/use-after-free explanation more specifically than the earlier teardown
race hypothesis. The retained app evidence does not itself prove which AudioUnit
initialization operation failed, so it does not conclusively identify the app's
root cause.

The full, unmodified two-commit PR patch is retained at
[`dependency-patches/mpv-0.41.0-coreaudio-init-failure.patch`](dependency-patches/mpv-0.41.0-coreaudio-init-failure.patch).
It adds partial-initialization cleanup and moves callback registration after
successful AudioUnit initialization. Both commits are necessary; fetching only
`merge_commit_sha` returns the registration-order change alone for this rebased PR.
The PR's original commits are `e8414d910311ea5663d5a230e85d48a415e6119a` and
`3371b9007754c3aefe719c97ab08325f23e14e88`; its reported final merged commit is
`c5d391adba7bd024954d0df1e0405f5749f4d4ca`.
