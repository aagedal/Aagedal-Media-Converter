# 4.5 submission recovery validation — 2026-09-19

## Scope

An accepted job previously remained queued indefinitely if its initial snapshot
write failed: retries found the in-memory acceptance and returned it without
performing the missing execution handoff.

The service now retains that handoff by job identity. A successful submission
retry saves the state and consumes the handoff once, for both the original plan
and an equivalent plan with the same requester/idempotency identity. Terminal
transitions discard pending handoffs alongside output reservations, so cancelled
work cannot restart. Recovery requires a submission retry; it does not introduce
automatic background retries. Restart behavior remains interruption of persisted
unfinished work. No wire schema, binaries, or dependencies changed.

## Validation

- Debug build and all 74 ApplicationJobContractTests passed.
- A directory substituted at the snapshot file path forces repeated atomic-save

- Restoring the writable path and retrying either plan executes the original job
  once, and further retries preserve its terminal result.
- Cancellation before recovery remains terminal through both retry routes.
- Reloading the saved snapshot preserves successful outputs or cancellation.
