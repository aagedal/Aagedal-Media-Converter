# 4.5 running-state persistence validation — 2026-09-19

## Scope

A job could remain running indefinitely when saving its running transition failed:
the in-memory registry had advanced, but the executor never received the job.
Submission retries could not recover it because its execution handoff had already
been consumed.

The execution boundary now makes that job failed (or cancelled when cancellation
has already been recorded), releases output reservations, and publishes the
terminal record even if the store remains unavailable. It does not launch FFmpeg
or automatically retry the conversion. After storage recovers, a submission retry
persists and returns the same terminal identity. A new request can use the
unproduced output. No wire schema, dependencies, or bundled binaries changed.

A persistently unavailable store cannot retain the new terminal result across
restart. Existing recovery semantics still interrupt unfinished work from the
last successfully saved snapshot.

## Validation

- Debug build and all 75 ApplicationJobContractTests passed.
- A regression holds the execution gate until acceptance is saved, then replaces
  the snapshot file with a directory to force the running-state save to fail.
- The executor does not start; the job becomes failed and reaches queue observers.
- Restoring storage and retrying retains the same failed job, including after
  loading the saved snapshot into a new service.
- A new request for the same output succeeds, proving both reservation release
  and continued execution-queue operation.
- The final observer assertion uses a bounded timeout.
