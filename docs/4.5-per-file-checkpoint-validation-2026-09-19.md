# 4.5 per-file checkpoint validation — 2026-09-19

## Scope

The shared FFmpeg adapter now awaits an output-history checkpoint after each
successful source conversion and before starting another source. The service
validates a growing prefix of the accepted plan, saves the existing job snapshot,
and publishes the updated record. Ordinary progress callbacks remain transient.
No persisted schema change is needed: active jobs use the existing outputURLs
field, and restart recovery retains those URLs when marking jobs interrupted.

Cancellation retains completed outputs when entering cancelling. A checkpoint
can still arrive during cancellation after successful publication. Terminal jobs
reject late checkpoints, and invalid or regressing executor results fail without
erasing previously checkpointed outputs. A checkpoint error stops the adapter
before another source starts, retaining the completed outputs in its failure
result. Persistent storage failure can still prevent durable recovery; the
adapter does not continue a batch after encountering that failure.

The visible queue marks checkpointed source rows done while later sources are
still running. Unfinished rows continue to follow the overall job state.

## Remaining release gates

There is still a window between FFmpeg publishing a file and the app saving its
checkpoint. This change does not provide atomic filesystem/history publication
or restart partially completed batches. Live visual review of mixed-result rows,
in-app playback, named-client workflows, real grant recovery, specialized-job
coexistence, and Developer ID signing/notarization remain open.

No bundled binaries or dependencies were changed. An unrelated localization
catalog edit appeared during the session and was left intact.
