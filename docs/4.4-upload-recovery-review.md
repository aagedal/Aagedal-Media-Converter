# 4.4 upload cancellation and destination review — 2026-09-12

## Confirmed correction

The in-process upload queue and cross-process lease used different destination
normalization. The queue recognized `media.example` and `MEDIA.EXAMPLE.` as the
same host, but the lease hashed them differently. Equivalent S3 endpoint spellings
such as `https://s3.example` and `HTTPS://S3.EXAMPLE.:443/` also acquired separate
locks. Two cooperating app processes could therefore write the same object at
once. The lease additionally rejected concurrent uploads of case-distinct S3
object names even though the queue correctly treated them as different objects.

`RemoteUploadLease` now hashes fixed-order components from the same
`UploadDestinationIdentity` used by `UploadManager`. Hostname spelling, default
ports, and S3 endpoints share normalization. Filesystem backends retain conservative
case folding, while S3 retains object-name case. Canonical Unicode is encoded
consistently with Swift string equality. Credentials remain excluded from the
identity and lock filenames contain only a digest.

The key format has changed from the earlier development implementation. Concurrent
coordination requires all participating app processes to run the updated build;
older development processes must be restarted. Existing persistent lock files are
left intact. This does not extend coordination to other clients, different app
containers, server aliases, or machines.

## Cancellation and output-reader disposition

The bounded review traced `UploadManager` attempt ownership and predecessor chains,
`RcloneService` cancellation boundaries and security-scope lifetime, and conversion's
calls to `cancelUploadBeforeConversion`. Existing regression coverage exercises
immediate cancellation, rapid replacement with late callbacks, invalid retries,
conversion teardown, output-to-source replacement, row/output changes, manager
release, enqueue ordering, and scope retention until the subprocess drains.
No additional reproducible cancellation or output-reader defect was found in this
review. No live transfer or new claim of remote conditional-write ownership is made.

## Evidence

- The production lease and destination identity are compiled into a separate-process
  Swift harness by `scripts/tests/test_remote_upload_coordination.py`.
- Before the fix, new regressions reproduced both equivalent endpoint overlaps
  (SFTP and S3) and the false conflict between case-distinct S3 objects.
- After the fix, all five process tests pass, including separate hostname/default-port
  aliases, S3 endpoint aliases, rejection followed by retry, distinct objects,
  and release after SIGKILL without replacing the persistent lock inode.
- Command: `DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer python3 -m unittest discover -s scripts/tests -p test_remote_upload_coordination.py -v`.
- Integrated Xcode validation is coordinated by the parent release-preparation task;
  this document alone does not claim a fresh app-suite pass.

Live authenticated upload/cancel/retry against supported backend servers and real
sandbox bookmark renewal remain manual release gates.
