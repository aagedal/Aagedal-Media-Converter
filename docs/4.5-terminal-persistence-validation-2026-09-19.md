# 4.5 terminal-state persistence validation — 2026-09-19

## Scope

A completed or cancelled job could remain visibly active when saving its state
failed. The registry had already changed and output reservations were released,
but queue observers received no update because publication followed the failed
write. The running-state recovery path had its own workaround for this problem.

Accepted lifecycle changes now share a persistence/publication helper: observers
receive the current in-memory records even when the snapshot write fails, and
the original storage error still reaches the caller. This covers transitions,
cancellation, interruption, and completed-output checkpoints. Checkpoint failures
still stop the executor before another source begins. The running-state recovery
path uses the same behavior instead of publishing separately.

This does not make failed writes durable. A restart before a successful later
save still recovers from the last saved snapshot. Retrying the submitted plan
after storage recovers saves the existing terminal result without executing it
again. No wire schema, dependencies, or bundled binaries changed.
